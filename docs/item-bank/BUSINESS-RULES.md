# item-bank-php 비즈니스 규칙 후보

대상: `legacy/item-bank-php`. 모듈 구조는 [ARCHITECTURE.md](ARCHITECTURE.md), 테이블 · 뷰는 [ERD.md](ERD.md) 를 따른다. 근거는 `파일:줄번호` 로 적고, 경로가 없는 파일명은 `legacy/item-bank-php/` 기준이다. 스키마는 `db/mariadb/init/01-schema.sql`(아래 `01-schema.sql`)이다.

분석 방법: `search.php` · `register.php` · `units.php` 의 조건문 · SQL 과 `01-schema.sql` 의 뷰 정의를 읽었다. 최초 작성 때는 실행하지 않았고, [CROSS-CHECK.md](CROSS-CHECK.md) 와 교차 검증할 때 실행 중인 로컬 컨테이너(`item-bank` :8081, `mariadb` :3306)에 **GET 검색 요청 · SELECT · `php -r` 만** 보내 일부 규칙을 확인했다(11절). 등록(POST)은 DB 에 쓰기 때문에 실행하지 않았다.

확신도 기준
- **확실**: 코드의 조건문 · SQL 로 동작을 확인했다.
- **추정**: 이름 · 주석 · 문구로 짐작했다.

작성 원칙
- 코드에 없는 규칙은 쓰지 않았다.
- 주석과 코드가 다르면 코드 기준으로 규칙을 쓰고 주석은 비고에 남겼다.
- 근거가 주석뿐인 것은 규칙으로 올리지 않고 8절에 "주석만 있음"으로 모았다.

주의가 필요한 것
- **BR-11**: 난이도를 비우면 `level < 5` 로 난이도 5 문항이 빠진다. 바로 위 주석은 "1~5 모두 포함"이라고 한다.
- **BR-12**: 난이도에 `3a` 같은 값을 넣으면 경고와 함께 난이도 3 으로 검색된다(PHP `(int)` 캐스팅, 실행 확인).
- **BR-09**: 소문자 단원 코드(`m5-1`)도 대문자와 같은 결과가 나온다(콜레이션 `utf8mb4_unicode_ci`, 실행 확인). 코드 주석의 "대개 0건"은 형식이 틀린 경우에만 맞다.
- **BR-37 vs BR-11**: 단원 목록의 "공개 문항 수"는 난이도 5 를 세고, 조건 없는 검색은 난이도 5 를 빼서 두 화면의 건수가 다를 수 있다.
- **수정 기능 없음**: 모듈 전체에 `UPDATE` 문이 없다. 수정 시 검증 규칙은 추출할 코드가 없다(6절).

## 1. 검색 공통 · 노출 대상

### BR-01 검색은 공개 문항만 대상으로 한다
- 규칙: 문항의 `status` 가 `'A'` 이면 검색 대상에 넣고, 그 밖의 값이면 뺀다.
- 근거: `search.php:522`, `01-schema.sql:68-70`
- 근거 코드:
  ```php
  $from   = " FROM v_item_public";
  ```
  ```sql
  FROM item i
  JOIN unit u ON u.id = i.unit_id
  WHERE i.status = 'A';
  ```
- 확신도: 확실
- 비고: CX-13 은 뷰 정의가 `legacy/item-bank-php/` 밖에 있어 필터 조건을 "확인 불가"로 두었다. 교차 검증 때 `01-schema.sql:52-70` 을 다시 읽어 `WHERE i.status = 'A'` 를 확인했으므로 이 규칙은 그대로 둔다. `'A'` 의 의미(공개)는 스키마 주석(`01-schema.sql:26`)에만 있다. `units.php:17` 은 같은 기준을 뷰를 거치지 않고 SQL 에 직접 쓴다(BR-37). 뷰가 `JOIN unit` 이라 단원이 없는 문항은 나올 수 없지만, `item.unit_id` 가 NOT NULL + FK 라 실제로는 차이가 없다.

### BR-02 검색 조건은 모두 AND 로 결합한다
- 규칙: 키워드 · 단원 · 난이도 · 태그가 여러 개 주어지면 모든 조건을 동시에 만족하는 문항만 보여 준다.
- 근거: `search.php:44`, `search.php:98`, `search.php:118`, `search.php:215`, `search.php:218`, `search.php:244`, `search.php:525-526`
- 근거 코드:
  ```php
  $where    = " WHERE 1=1";
  $where .= " AND unit_code = ?";
  $where .= " AND EXISTS (SELECT 1 FROM item_tag it JOIN tag t ON t.id = it.tag_id"
  ```
  ```php
  $sql      = $select . $from . $where . $orderBy . $limit;
  $countSql = "SELECT COUNT(*) AS cnt" . $from . $where;
  ```
- 확신도: 확실
- 비고: OR 조합은 키워드 내부(제목 OR 지문, BR-05)에만 있다. 목록 SQL 과 건수 SQL 은 같은 `$where` 를 쓰므로 건수와 목록의 조건이 같다(CX-08 교차 확인).

### BR-03 파라미터가 배열로 오면 첫 값만 쓴다
- 규칙: `q · unit · level · tag · sort · dir · page` 가 배열이면 첫 번째 값만 조건으로 쓴다. 따라서 단원 · 난이도 · 태그는 각각 한 개만 지정할 수 있다.
- 근거: `search.php:55`, `search.php:59`, `search.php:63`, `search.php:67`, `search.php:71`, `search.php:75`, `search.php:79`
- 근거 코드:
  ```php
  $tag = is_array($params['tag']) ? (string)reset($params['tag']) : (string)$params['tag'];
  ```
- 확신도: 확실
- 비고: 다중 태그 · 다중 단원 검색은 없다.

### BR-04 잘못된 검색 입력은 막지 않고 경고와 함께 그대로 검색한다
- 규칙: 단원 코드 형식 · 대소문자 · 미등록 단원 · 범위 밖 난이도 · 미등록 태그 · 알 수 없는 정렬이면 경고를 표시하고 검색은 계속한다.
- 근거: `search.php:111-117`, `search.php:141-142`, `search.php:223-229`, `search.php:250-260`, `search.php:322-326`, `search.php:510-516`
- 근거 코드:
  ```php
  // 형식이 달라도 그대로 조회한다 (결과는 대개 0건)
  $warnings[] = '단원 코드 형식이 올바르지 않습니다. (예: M5-1)';
  ```
- 확신도: 확실
- 비고: 경고는 `<ul id="warnings">` 로 출력한다(`search.php:511`). 검색 화면에는 입력 오류로 검색을 거부하는 분기가 없다. 예외는 바인딩 개수 불일치 한 가지로, 이때만 `RuntimeException` 을 던진다(`search.php:536-539`).

## 2. 검색 조건: 키워드

### BR-05 키워드는 제목 또는 지문의 부분 일치로 찾는다
- 규칙: 앞뒤 공백을 뺀 키워드가 비어 있지 않으면 `title` 또는 `stem` 에 키워드가 포함된 문항을 찾는다.
- 근거: `search.php:85`, `search.php:90`, `search.php:97-98`
- 근거 코드:
  ```php
  $like = '%' . $q . '%';
  $where .= " AND (title LIKE ? OR stem LIKE ?)";
  ```
- 확신도: 확실
- 비고: 한 글자 키워드도 검색한다. 경고만 붙는다(`search.php:91-93`).

### BR-06 키워드가 100자를 넘으면 100자로 자른다
- 규칙: 공백을 뺀 키워드가 100자를 넘으면 앞 100자만 쓰고 경고를 표시한다.
- 근거: `search.php:86-89`, `search.php:494`
- 근거 코드:
  ```php
  if (mb_strlen($q, 'UTF-8') > 100) {
      $q = mb_substr($q, 0, 100, 'UTF-8');
  ```
- 확신도: 확실
- 비고: 매직 넘버 `100`. 폼의 `maxlength="100"`(`search.php:494`)과 같은 값이 두 곳에 따로 있다.

### BR-07 키워드의 `%` · `_` 는 이스케이프하지 않고 와일드카드로 쓴다
- 규칙: 키워드에 `%` 나 `_` 가 있으면 경고를 표시하고 LIKE 와일드카드로 그대로 쓴다.
- 근거: `search.php:94-97`
- 근거 코드:
  ```php
  if (strpos($q, '%') !== false || strpos($q, '_') !== false) {
      $warnings[] = '키워드의 % 와 _ 는 와일드카드로 처리됩니다.';
  ```
- 확신도: 확실
- 비고: 이관 시 이스케이프를 추가하면 결과가 달라진다. 레거시 동작을 유지할지 결정해야 한다.

## 3. 검색 조건: 단원 · 난이도 · 태그

### BR-08 단원은 단원 코드와 정확히 일치하는 문항만 찾는다
- 규칙: 앞뒤 공백을 뺀 단원 값이 비어 있지 않으면 `unit_code = 입력값` 인 문항만 찾는다.
- 근거: `search.php:109-110`, `search.php:118-120`
- 근거 코드:
  ```php
  $where .= " AND unit_code = ?";
  $types .= 's';
  $values[] = $unit;
  ```
- 확신도: 확실
- 비고: 검색 파라미터는 단원 `id` 가 아니라 `code` 다. 등록 화면은 `id` 를 받는다(BR-30).

### BR-09 단원 코드 형식 · 대소문자가 달라도 입력값 그대로 조회하며, 대소문자는 DB 에서 무시된다
- 규칙: 단원 코드가 `^[A-Za-z][0-9]{1,2}-[0-9]{1,2}$` 형식이 아니거나 소문자를 포함하면 경고를 표시하고, 입력값을 바꾸지 않고 조회한다. DB 비교는 대소문자를 무시하므로 `m5-1` 은 `M5-1` 과 같은 문항을 찾는다.
- 근거: `search.php:111-120`, `01-schema.sql:13`, `01-schema.sql:18`, `01-schema.sql:56`
- 근거 코드:
  ```php
  if (!preg_match('/^[A-Za-z][0-9]{1,2}-[0-9]{1,2}$/', $unit)) {
      // 형식이 달라도 그대로 조회한다 (결과는 대개 0건)
  if ($unit !== strtoupper($unit)) {
      $warnings[] = '단원 코드는 대문자로 입력하세요. (입력값 그대로 조회합니다)';
  }
  $where .= " AND unit_code = ?";
  ```
  ```sql
  code  VARCHAR(16)  NOT NULL,
  ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
  u.code  AS unit_code,
  ```
- 확신도: 확실 (실행 확인)
- 비고:
  - 실행 결과: `search.php?unit=M5-1&level=3` 과 `unit=m5-1&level=3` 이 모두 1건이고, 소문자 쪽에만 대문자 경고가 붙었다. `SELECT COUNT(*) FROM v_item_public WHERE unit_code='m5-1'` 도 `'M5-1'` 과 같은 6건이다.
  - 주석(`search.php:112`)의 "결과는 대개 0건"은 형식 자체가 틀린 입력에만 맞다. CX-03 은 이 주석을 따라 소문자도 "대개 0건"으로 적었는데, 실행 결과와 다르다.
  - 단원 이름을 찾는 PHP 비교(`search.php:162`, `===`)는 대소문자를 구분하므로 폼의 선택 상태는 풀린다.

### BR-10 등록되지 않은 단원 코드면 경고를 표시한다
- 규칙: `unit` 테이블에서 코드를 찾지 못하면 "등록되지 않은 단원 코드입니다" 경고를 표시하고, 찾으면 요약에 단원 이름과 학년을 붙인다.
- 근거: `search.php:125`, `search.php:132-134`, `search.php:141-146`
- 근거 코드:
  ```php
  $stmt = $conn->prepare("SELECT name, grade FROM unit WHERE code = ?");
  if ($unitName === '') {
      $warnings[] = '등록되지 않은 단원 코드입니다: ' . $unit;
  ```
- 확신도: 확실
- 비고: 이 조회는 요약 · 경고용이다. 검색 SQL 은 이 결과와 관계없이 BR-08 조건으로 실행된다.

### BR-11 난이도가 비어 있으면 난이도 5 를 뺀다
- 규칙: 앞뒤 공백을 뺀 난이도가 빈 값이면 `level < 5` 조건을 붙여 난이도 1~4 문항만 보여 준다.
- 근거: `search.php:211`, `search.php:213-216`
- 근거 코드:
  ```php
  // 난이도 값이 비어 있으면 전체 난이도 검색 (1~5 모두 포함)
  if ($level == '') {
      $where .= " AND level < 5";
  ```
- 확신도: 확실
- 비고:
  - **주석과 코드가 다르다.** 주석은 "1~5 모두 포함", 코드는 5 를 제외한다. 규칙은 코드 기준으로 썼다. 의도인지 버그인지는 미확인이다(ARCHITECTURE.md 6절과 같은 발견).
  - 매직 넘버 `5`. 폼 기본 선택지의 이름도 '전체'다(`search.php:192`).
  - 이 조건은 요약에 나오지 않는다. 다른 조건이 없으면 "조건 없이 검색했습니다"라고 표시한다(`search.php:355-356`).
  - `level` 파라미터가 아예 없어도 같은 분기를 탄다(`search.php:61`, 기본값 `''`).
  - 실행 확인: 뷰 `v_item_public` 의 난이도별 건수는 1~4 가 각 5건, 5 가 6건(합 26건)인데, 조건 없이 검색하면 "검색 결과 20건"이다. 난이도 5 의 6건이 빠진다. CX-04 도 같은 결론이다.

### BR-12 난이도가 1~5 한 자리면 그 난이도와 같은 문항만 찾고, 그 밖의 값은 정수로 바꿔 비교한다
- 규칙: 난이도가 `^[1-5]$` 이면 `level = 값` 으로 찾는다. 그 밖의 값이면 경고를 표시하고 `(int)` 로 바꾼 값으로 `level = ?` 비교를 한다.
- 근거: `search.php:217-229`
- 근거 코드:
  ```php
  else if (preg_match('/^[1-5]$/', $level)) {
      $where .= " AND level = ?";
  ```
  ```php
  $warnings[] = '난이도는 1~5 사이여야 합니다.';
  $where .= " AND level = ?";
  $values[] = (int)$level;
  ```
- 확신도: 확실 (실행 확인)
- 비고:
  - 주석(`search.php:224`)은 "1~5 밖의 값은 … 대개 0건"이라고 한다. 하지만 PHP 7.4 의 `(int)` 는 숫자로 시작하는 문자열의 앞 숫자만 취한다. 그래서 `3a` · `05` · `4.9` 는 경고와 함께 각각 난이도 3 · 5 · 4 로 검색된다. CX-06 은 주석처럼 "대개 0건"으로 적었는데, 실행 결과와 다르다.
  - 실행 확인: 컨테이너의 PHP 는 7.4.33 이고, `(int)"3a"`=3, `(int)"05"`=5, `(int)"4.9"`=4, `(int)"abc"`=0 이다. 검색 건수는 `level=3` 5건, `level=3a` 5건, `level=05` 6건(난이도 5 전체), `level=4.9` 5건, `level=abc` 0건이다. `level=3` 만 빼고 모두 "난이도는 1~5 사이여야 합니다." 경고가 붙었다.
  - 숫자가 아닌 값(`abc`)은 0 이 되어 `level = 0` 으로 0건이 된다.
  - 난이도 1~5 경계는 `register.php:70` 에도 같은 정규식으로 따로 구현되어 있다.

### BR-13 태그는 이름이 정확히 일치하는 태그가 붙은 문항만 찾는다
- 규칙: 앞뒤 공백을 뺀 태그가 비어 있지 않으면 그 이름의 태그가 연결된 문항만 찾는다.
- 근거: `search.php:235-236`, `search.php:244-247`
- 근거 코드:
  ```php
  $where .= " AND EXISTS (SELECT 1 FROM item_tag it JOIN tag t ON t.id = it.tag_id"
          . " WHERE it.item_id = v_item_public.id AND t.name = ?)";
  ```
- 확신도: 확실
- 비고: 검색 파라미터는 태그 `id` 가 아니라 `name` 이다. 등록 화면은 `id` 를 받는다(BR-32). 대소문자는 BR-09 와 같은 콜레이션 문제가 있을 수 있다(추정).

### BR-14 태그에 `%` · `_` 가 있어도 부분 일치로 찾지 않는다

### BR-24 페이지 번호는 1~999 로 보정한다
- 규칙: 페이지가 숫자가 아니면 1페이지를 보여 준다. 1 보다 작으면 1, 999 보다 크면 999 로 바꾼다.
- 근거: `search.php:336-348`
- 근거 코드:
  ```php
  if (preg_match('/^[0-9]+$/', $pageRaw)) {
  if ($page > 999) {
      $page = 999;
  ```
- 확신도: 확실
- 비고:
  - 매직 넘버 `999`.
  - 경고 조건이 경우마다 다르다. 숫자가 아닌 값은 경고한다. 빈 값과 `'1'` 은 경고하지 않는다(`search.php:339`). `0` 은 경고 없이 1 로 바꾼다(`search.php:342-344`). 999 초과는 경고한다. 음수(`-1`)는 `^[0-9]+$` 에 맞지 않아 "숫자가 아닌 값"으로 경고한다.
    ```php
    if (preg_match('/^[0-9]+$/', $pageRaw)) {
        $page = (int)$pageRaw;
    } else if ($pageRaw !== '' && $pageRaw !== '1') {
        $warnings[] = '페이지 번호가 올바르지 않아 1페이지를 표시합니다.';
    }
    if ($page < 1) {
        $page = 1;
    }
    ```
  - 실행 확인: `page=0` 경고 없음, `page=-1` · `page=abc` "페이지 번호가 올바르지 않아 1페이지를 표시합니다.", `page=1000` "페이지 번호는 999 를 넘을 수 없습니다.". CX-12 는 "1 미만이면 1페이지로 맞추고 경고"로 읽히는데, `0` 은 경고하지 않으므로 이 문서의 기술을 유지한다.
  - 총 페이지 수를 넘는 페이지는 보정하지 않는다. 이때 건수는 1건 이상이지만 본문 행이 없는 표가 나온다(`search.php:657`, `search.php:672`). 코드 흐름으로 본 추정이다.

### BR-34 새 문항 id 는 전체 문항의 최대 id + 1 이다
- 규칙: 트랜잭션 안에서 `item` 전체의 `MAX(id) + 1` 을 잠금 조회해 새 문항 id 로 쓰고, 문항이 없으면 1 을 쓴다.
- 근거: `register.php:85`, `register.php:87-90`
- 근거 코드:
  ```php
  $res = $conn->query("SELECT COALESCE(MAX(id), 0) + 1 AS next_id FROM item FOR UPDATE");
  $newId = (int)$row['next_id'];
  ```
- 확신도: 확실
- 비고: `item.id` 가 AUTO_INCREMENT 가 아니다(`01-schema.sql:21`). 상태(`A · R · D`)와 관계없이 전체 행을 기준으로 한다.

### BR-35 새 문항은 검수중(`R`) 상태로 저장하고, 생성 · 수정 시각을 현재 시각으로 넣는다
- 규칙: 등록한 문항은 `status = 'R'`, `created_at = updated_at = NOW()` 로 저장한다. 따라서 BR-01 에 의해 검색에 나오지 않는다.
- 근거: `register.php:84`, `register.php:93-94`
- 근거 코드:
  ```php
  "INSERT INTO item (id, unit_id, title, stem, level, status, created_at, updated_at)
   VALUES (?, ?, ?, ?, ?, 'R', NOW(), NOW())"
  ```
- 확신도: 확실
- 비고: CX-20 은 뷰 정의를 보지 못해 "검색에서 빠지는지는 미확정"으로 두었다. 뷰가 `WHERE i.status = 'A'`(`01-schema.sql:70`)이므로 `R` 문항은 검색에서 빠진다는 이 문서의 기술을 유지한다. 실제 등록 후 검색은 DB 쓰기가 필요해 실행하지 않았다(정적 확인). 스키마 기본값은 `'A'`(`01-schema.sql:26`)지만 INSERT 에 `'R'` 을 명시해 쓰지 않는다. `'R'` 의 의미(검수중)는 주석(`register.php:84`, `01-schema.sql:26`)과 안내 문구(`register.php:116`)로 짐작한 것이다. `R → A` 로 바꾸는 코드는 모듈에 없다(ERD.md 4절).

### BR-36 문항과 태그 연결은 한 트랜잭션으로 저장하고, 하나라도 실패하면 모두 되돌린다
- 규칙: `item` INSERT 와 `item_tag` INSERT 중 하나라도 실패하면 롤백하고 "저장 중 오류가 발생했습니다"를 보여 준다. 성공하면 커밋하고 폼을 비운다.
- 근거: `register.php:85`, `register.php:99-101`, `register.php:108-110`, `register.php:114-123`
- 근거 코드:
  ```php
  } catch (Exception $e) {
      $conn->rollback();
      $errors[] = '저장 중 오류가 발생했습니다.';
  ```
- 확신도: 확실
- 비고: 성공 문구는 "문항 #id 을(를) 등록했습니다. 검수 완료 후 검색에 노출됩니다."다(`register.php:116`). 폼 비우기는 `register.php:117-118` 에서 한다.

## 7. 단원 목록

### BR-37 단원 목록의 문항 수는 공개(`A`) 문항만 센다
- 규칙: 단원마다 `status = 'A'` 인 문항 수를 세어 "공개 문항 수"로 보여 준다. 문항이 0개인 단원도 목록에 나온다.
- 근거: `units.php:15-19`, `units.php:36`
- 근거 코드:
  ```php
  // 단원별 공개(status='A') 문항 수. 삭제 · 검수중 문항은 세지 않는다.
  (SELECT COUNT(*) FROM item i WHERE i.unit_id = u.id AND i.status = 'A') AS item_count
  ```
- 확신도: 확실
- 비고: 바로 위 주석(`units.php:15`)은 "삭제 · 검수중 문항은 세지 않는다"고 한다. 코드는 `'A'` 만 세므로 `D` · `R` 을 세지 않는다는 점은 코드와 맞다. 다만 `D`=삭제, `R`=검수중이라는 **의미**는 이 주석과 스키마 주석(`01-schema.sql:26`)에만 있다(8절). CX-14 는 이 주석 문장을 규칙 본문에 넣었다. **같은 공개 기준이 두 곳에 다르게 구현되어 있다.** 검색은 뷰(`01-schema.sql:70`)를, 단원 목록은 직접 쓴 SQL 을 쓴다. 단원 목록은 난이도 5 를 세지만 조건 없는 검색은 난이도 5 를 뺀다(BR-11). 그래서 같은 단원이라도 단원 목록 건수와 난이도를 비운 검색의 건수가 다를 수 있다.

### BR-38 단원은 학년 오름차순, 같은 학년이면 코드 오름차순으로 나열한다
- 규칙: 단원 목록 · 검색 폼 단원 선택 · 등록 폼 단원 선택은 모두 `grade ASC, code ASC` 로 나열한다.

## 10. 미확인

- **BR-11 `level < 5` 가 의도된 규칙인지 버그인지.** 주석과 코드가 다르다. 이관 전에 담당자 확인이 필요하다.
- **BR-13 · BR-16 태그 대소문자 구분.** 단원 코드(BR-09)는 실행으로 대소문자 무시를 확인했다. 태그도 같은 콜레이션(`01-schema.sql:40`)이라 같을 것으로 추정하지만, 태그로는 실행해 보지 않았다.
- **BR-32 태그 id 중복 제출 시 동작.** PK 충돌로 롤백될 것으로 추정했다. 확인하려면 POST(DB 쓰기)가 필요해 실행하지 않았다.
- **BR-35 등록 직후 문항이 검색에 안 나오는지.** 뷰 정의로 정적 확인만 했다. 실행 확인에는 POST 가 필요하다.
- **`R → A`(검수 완료) · `D`(삭제) 전이 경로.** 이 모듈 밖이다(ERD.md 4절).
- `characterization/` 스냅샷이 위 규칙 중 어느 것을 고정하고 있는지는 이번 범위에서 확인하지 않았다.

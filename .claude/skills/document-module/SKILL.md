# 레거시 모듈 문서화

## 반드시 지킬 것
- 분석 대상 폴더(`$ARGUMENTS` 의 모듈 경로)의 파일은 읽기만 한다. 수정 · 삭제 · 포맷팅하지 않는다.
- 범위 제한이 있으면 그 범위 밖 파일은 분석하지 않고, 문서 머리말에 범위를 적는다.
- 단계가 끝날 때마다 결과를 파일로 저장한 뒤 다음 단계로 넘어간다. 저장하지 않은 채 다음 단계를 시작하지 않는다.
- 근거는 모두 `파일:줄번호` 로 적고, 경로가 모듈 밖이면(예: `db/mariadb/init/01-schema.sql`) 전체 경로를 쓴다.

## 산출물 위치
- `docs/<모듈명>/ARCHITECTURE.md`, `docs/<모듈명>/ERD.md`, `docs/<모듈명>/BUSINESS-RULES.md`
- `<모듈명>` 은 폴더 이름이 아니라 아래 셋 중 하나다. 목록에 없는 경로면 멈추고 사람에게 묻는다.
  - `legacy/item-bank-php` → `item-bank`
  - `legacy/assignment-thymeleaf` → `assignment`
  - `legacy/grade-mssql` → `grade`

## 절차
1. **계획 제시**: 대상 파일 목록 · 단계 순서 · 단계별로 저장할 파일 · 실행 확인 여부를 답변으로 보여 주고 승인을 받은 뒤 시작한다.
2. **진입점**: 요청을 받는 파일 · 컨트롤러 · 메인 클래스와 URL(또는 실행 명령)을 표로 정리한다.
   → `ARCHITECTURE.md` 의 모듈 개요 · 폴더 구조 · 진입점 절에 저장.
3. **의존 관계**: include/import · 호출 관계, 외부 설정 · DB 접속을 호출하는 쪽 → 호출되는 쪽 방향으로 적는다.
   → `ARCHITECTURE.md` 의 의존 관계 절에 추가 저장.
4. **데이터 흐름**: 테이블 · 뷰 목록, 관계(FK · 조인), 파일별 읽기 · 쓰기 위치를 스키마 파일과 SQL 로 정리한다.
   → `ERD.md` 에 저장(테이블 목록 · 관계(Mermaid erDiagram) · 읽기 · 쓰기 위치 · 미확인).
5. **비즈니스 규칙 후보**: 조건문 · SQL · 검증 로직에서 규칙을 뽑아 아래 형식으로 쓴다.
   → `BUSINESS-RULES.md` 에 저장. 머리말에 확신도 기준과 요약 표(구분 · 규칙 ID 범위)를 둔다.
6. **표본 점검 추천**: 사람이 표본 점검할 규칙 3개를 추천한다. 1개는 "가장 그럴듯한" 규칙(코드가 명확해 보여 검증 없이 넘어가기 쉬운 것)을 반드시 넣고, 나머지는 주석과 코드가 다른 규칙 · 추정 규칙에서 고른다. 각 규칙에 확인 방법(재독할 줄 · 실행할 GET 요청이나 SELECT)을 붙인다.
   → `BUSINESS-RULES.md` 끝 "표본 점검 추천" 절에 저장하고 답변에도 요약한다.

## 규칙 형식
```markdown
### BR-01 <한 줄 요약>
- 규칙: <입력 · 조건 → 결과를 한 문장으로>
- 근거: `파일:줄번호`, `파일:시작-끝`
- 근거 코드:
  ```<언어>
  <근거 줄을 그대로 인용>
  ```
- 확신도: 확실 | 추정
- 비고: <주석과 코드의 차이, 실행 확인 여부, 관련 규칙 ID>
```
- 확실: 조건문 · SQL 로 동작을 확인했다. 추정: 이름 · 주석 · 문구로 짐작했다.
- 실행으로 확인했으면 "확실 (실행 확인)"으로 적고, 어떤 요청 · 쿼리로 확인했는지 비고에 남긴다.

## 하지 말 것 (item-bank 검증 이력에서 실제로 틀린 유형)
- 주석을 규칙으로 옮기지 않는다. 주석의 "대개 0건"(BR-09 · BR-12)과 "1~5 모두 포함"(BR-11)은 코드 · 실행 결과와 달랐다. 주석과 코드가 다르면 코드 기준으로 쓰고 주석은 비고에 둔다.
- 경계값을 뭉뚱그리지 않는다. "1 미만이면 경고"(CX-12)는 틀렸다 — `0` 은 경고 없음, `-1` 은 경고였다. `<` · `<=` · `empty()` · 캐스팅을 줄 단위로 확인한다.
- 모듈 폴더 밖에 있다는 이유로 "확인 불가"로 두지 않는다. 뷰 · 스키마(`db/mariadb/init/01-schema.sql`)를 읽으면 확인되는 것이 있었다(BR-01 · BR-35).
- 콜레이션 · 타입 캐스팅처럼 DB · 언어가 결정하는 동작을 코드 조건문만 보고 단정하지 않는다(BR-09 대소문자 무시, BR-12 `3a` → 3).
- 근거 줄번호만 적고 인용을 빼지 않는다. 인용이 없으면 검증자가 확인할 수 없다(BR-02).
- 존재하지 않는 함수 · 파일을 쓰지 않는다. 적기 전에 Grep 으로 정의 위치를 찾는다.
- 호출 방향을 뒤집지 않는다. "A 가 B 를 include/호출한다"는 A 파일의 해당 줄로 확인한다.
- 코드에 없는 규칙(예: 수정 기능이 없는데 수정 검증 규칙)을 만들지 않는다. 없으면 "없음"과 근거를 적는다.
- 쓰기(POST · INSERT · UPDATE)를 실행해 확인하지 않는다. 실행 확인은 GET · SELECT 만 하고, 못 한 것은 "미확인" 절에 남긴다.

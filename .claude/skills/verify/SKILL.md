# 머지 전 검증

검증 대상: $ARGUMENTS

- 위 값이 비어 있으면 `git diff upstream/main...HEAD` 를 대상으로 삼는다.
- 값이 patch 파일이면 `git apply --stat <파일>` 로 목록을 뽑고 patch 본문을 diff 로 읽는다.
- 절차는 저장소 루트의 `templates/verification-loop.md` 를, 판정 항목은 저장소 루트의 `templates/approval-checklist.md` 를 따른다. 경로는 모두 저장소 루트 기준이다.

## 반드시 지킬 것

- **코드를 수정하지 않는다.** 보고만 한다. 고치기 시작하면 그 순간 "만든 쪽"이 된다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 "통과"라고 쓰지 않는다. 실행할 수 없었으면(서버 꺼짐, 의존성 미설치) 그 사실을 적고 사람에게 기동을 요청한다.
- 테스트 출력은 통과 · 실패 수와 실패한 테스트 이름만 대화에 남긴다. 전체 로그를 싣지 않는다.

## 1. 요청 범위 확인

- 이 변경이 무엇을 하려던 것인지 한 문장을 확보한다. 인자 · 대화 · PR 설명에서 찾는다.
- 찾을 수 없으면 **판정하지 말고** 사람에게 "요청 범위를 한 문장으로 알려 달라"고 먼저 묻고 멈춘다.

## 2. 변경 파일 목록과 diff 읽기

1. `git diff --stat <대상>` 으로 변경 파일 목록을 먼저 본다.
2. 파일마다 `git diff <대상> -- <파일>` 로 바뀐 줄을 읽는다. 판정에 필요하면 Read 로 파일 전체를 읽는다.
3. `git status --porcelain` 에 커밋되지 않은 변경 · 새 파일이 있으면 대상에 포함되지 않았다는 사실을 출력에 한 줄 적는다.

## 3. 체크리스트 대조

- 저장소 루트의 `templates/approval-checklist.md` 를 읽고, 항목마다 **충족 · 미충족 · 확인 필요** 중 하나로 표시한다.
- 심각도(치명 / 경고 / 제안)는 같은 파일의 "심각도 정의"를 따른다.
- 컨벤션 항목은 팀 `CLAUDE.md` 를 기준으로 보고, `convention-check` Skill 이 있으면 그 결과를 쓴다.

## 4. 테스트 실행

변경된 폴더의 테스트만 실행한다. 해당 폴더에 변경이 없으면 "해당 없음"으로 적는다.

| 변경된 폴더 | 명령 |
|---|---|
| `modern/api` | `cd modern/api && ./gradlew test` |
| `modern/web` | `cd modern/web && npm test` |
| 이관 코드(레거시 규칙을 `modern/` 으로 옮긴 변경) | `cd characterization && npm test` (레거시 대상)<br>`cd characterization && TARGET_BASE_URL=http://localhost:8080 npm test` (새 API 대상) |

- 출력은 임시 파일로 돌리고, 요약 줄만 뽑아 본다. 예:
  - `./gradlew test > "$LOG" 2>&1; echo "exit=$?"` 뒤 `grep -E "tests completed|FAILED|BUILD (SUCCESSFUL|FAILED)" "$LOG"`
  - `npm test > "$LOG" 2>&1; echo "exit=$?"` 뒤 `grep -E "Test Files|Tests |FAIL|×" "$LOG"`
- characterization 은 대상 서버(레거시 Compose 프로필 · `modern/api`)가 떠 있어야 한다. 연결이 거부되면 실패로 세지 말고 "실행 불가 — 서버 기동 필요"로 적고 사람에게 요청한다.
- 스냅샷 차이로 실패하면 실패한 케이스 이름과 차이를 그대로 적는다. `characterization/` 의 테스트 · `__snapshots__/` 를 고치라고 제안하지 않는다.

## 5. 승인 기준 판정

- 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 충족 · 미충족으로 판정한다.
- **하나라도 미충족이면 반려.** 요청 범위를 모르면 "요청 범위 이탈 없음"을 충족으로 표시하지 않는다.
- 이슈가 0건이면 경고 · 제안 수준까지 한 번 더 훑어본 뒤 확정한다.

## 출력 형식 (이 순서로 고정)

```
판정: 승인 | 반려

검증 대상: <범위>   요청 범위: <한 문장>

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수, 실패한 테스트 이름 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 이슈 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
|---|---|---|---|---|
| 1 | 치명 / 경고 / 제안 | `modern/api/.../X.java:42` | 무엇이 어떤 규칙에 어긋나는지 | 어떻게 고칠지 |

확인 필요
- 무엇을 더 봐야 판정할 수 있는지 한 줄씩
```

- 이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 칸을 모두 채운다.
- 이슈가 없으면 표 대신 "이슈 없음" 한 줄을 쓴다.

# 승인 체크리스트 v1

버전: v1 · 2회차 (3회차 Day 3-4에서 보안 항목 보강)
오늘 바뀐 점:
- 판정이 갈리던 네 문장("충분하다", "심각한 문제", "지나치게 많지 않다", "적절하게")을 예/아니오 문장으로 바꿨다.
- 치명 이슈를 네 종류로 한정하고, 범위 밖 변경 허용선과 컨벤션 위반의 무게를 정했다.
- 새 public 메서드 · 엔드포인트에는 테스트가 있어야 승인한다(getter · setter · 생성자 같은 접근자는 제외).

AI 가 만든 변경분 · 외주사 PR 을 머지하기 전에 리뷰어가 대조하는 목록이다. 네 기준이 **모두** 충족되어야 승인이다. 하나라도 미충족이면 반려.

## 팀 결정 (Day 2-1 실습 4)

- 테스트 통과: 기존 테스트 통과에 더해, 새로 생기거나 동작이 바뀐 public 메서드 · 엔드포인트마다 대응하는 테스트가 1개 이상 있어야 한다.
- 치명 이슈 정의: 비밀값 노출, 데이터 손실, 인증 · 권한 우회, SQL 문자열 조립. 이 네 종류만 치명이다.
- 범위 밖 변경: 요청으로 설명되는 파일 안의 import 정리만 허용한다. 요청에 없는 파일은 한 줄도 바꾸지 않는다.
- 컨벤션: 계층 규칙 위반(컨트롤러의 Repository · SQL 직접 호출)과 빈 catch 는 반려, 네이밍 · 형식 위반은 경고로 남기고 승인 여부에 영향을 주지 않는다.

## 심각도 정의

- **치명** — 비밀값 노출 · 데이터 손실 · 인증 · 권한 우회 · SQL 문자열 조립 중 하나. 1건이라도 있으면 반려.
- **경고** — 치명은 아니지만 체크리스트 항목에 "아니오"가 나온 것. 1 · 3절의 항목이 "아니오"이면 그 기준은 미충족(반려)이다. 4절과 "보안(경고)" 항목은 괄호 안의 표시를 따른다.
- **제안** — 체크리스트 항목에 걸리지 않는 개선 의견. 승인 · 반려에 영향을 주지 않는다. 목록으로만 남긴다.

이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 항목으로 적는다. 근거 줄번호를 댈 수 없는 지적은 "확인 필요"로 따로 둔다.

## 1. 테스트 통과

- [ ] 변경된 폴더의 테스트 명령을 실제로 실행했다(실행하지 않고 통과라고 쓰지 않는다).
- [ ] 실행 결과에 실패 · 오류가 0건이다.
- [ ] 새로 생기거나 동작이 바뀐 public 메서드 · 엔드포인트 · 컴포넌트마다 대응하는 테스트가 1개 이상 있다 (getter · setter · 생성자 같은 접근자는 제외)
- [ ] 이관 코드라면 `characterization` 의 `npm test` 가 레거시 대상과 새 API 대상(`TARGET_BASE_URL=http://localhost:8080`) 양쪽에서 통과했다.
- [ ] 기존 테스트를 지우거나 건너뛰게(`skip`, `@Disabled`) 바꾼 곳이 없다.
- [ ] `characterization/` 의 테스트 코드와 스냅샷 파일을 바꾸지 않았다(바꿨다면 요청에 명시돼 있다).

## 2. 치명 이슈 0건

- [ ] 비밀번호 · 토큰 · 키가 코드 · 설정 · 테스트 픽스처에 리터럴로 들어 있지 않다.
- [ ] SQL 을 문자열로 이어 붙여 만드는 곳이 없다(파라미터 바인딩 사용).
- [ ] 데이터를 지우거나 덮어쓰는 코드가 새로 생겼다면 요청에 그 내용이 명시돼 있다.
- [ ] 인증 · 권한 검사를 빼거나 우회하는 변경이 없다.

### 보안 (경고 — 3회차 시큐어코딩 체크리스트의 reviewer 항목. 아니오면 경고로 남기고, 이 항목만으로는 반려하지 않는다)

- [ ] 외부 입력(요청 파라미터 · 본문)의 타입 · 범위 · 길이를 서버에서 검증한다. 화면 검증만 있는 곳이 없다.
- [ ] 로그 · 응답에 학생 식별자(`STU-…`) · 이메일 · 토큰이 원문으로 나가지 않는다.
- [ ] 인증 · 권한 · 세션 처리 코드가 바뀌었다면 "보안 담당 확인 필요"로 표시했다.

## 3. 요청 범위 이탈 없음

- [ ] 요청 문장이 한 문장으로 확인되었다(없으면 판정하지 않고 먼저 묻는다).
- [ ] 변경 파일 목록의 모든 파일이 요청 문장으로 설명된다.
- [ ] 요청 문장으로 설명되지 않는 변경이 0줄이다. 예외는 요청으로 설명되는 파일 안의 import 정리뿐이다.
- [ ] 의존성 추가 · DB 스키마 변경 · 설정 파일 변경이 있다면 요청에 포함돼 있었다.

## 4. 컨벤션 준수

- [ ] 팀 `CLAUDE.md` 의 코딩 컨벤션과 금지 사항을 대조했다(`convention-check` Skill 이 있으면 그 결과를 쓴다).
- [ ] 컨트롤러에서 Repository · SQL 을 직접 호출하는 곳이 없다. (아니오면 반려)
- [ ] 예외를 잡고 아무 처리 없이 넘기는 곳이 없다. (아니오면 반려)
- [ ] `System.out.println` · `console.log` 같은 임시 출력이 남아 있지 않다. (아니오면 경고)
- [ ] 이름 · 형식 규칙(`CLAUDE.md` 2절 "이름 · 형식")을 지켰다. (아니오면 경고, 승인에 영향 없음)

## 판정 형식

첫 줄에 `판정: 승인` 또는 `판정: 반려`. 이어서 네 기준의 충족 · 미충족 표, 그다음 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향). 코드는 수정하지 않는다.

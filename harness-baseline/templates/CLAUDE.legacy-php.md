# CLAUDE.md — 레거시 유지보수 팀 템플릿

이 파일은 `templates/CLAUDE.legacy-php.md` 입니다. 저장소 루트의 `CLAUDE.md` 로 옮겨 쓰기 전에 팀 사정에 맞지 않는 줄을 고치세요.
대상 코드: `legacy/item-bank-php` (PHP 7.4 · mysqli · MariaDB 10.11). 같은 원칙을 `legacy/assignment-thymeleaf`, `legacy/grade-mssql` 에도 적용한다.

## 1. 실행 · 확인 명령

```bash
docker compose --profile php up -d                                   # 문항 은행 웹 + MariaDB → http://localhost:8081
docker compose --profile php logs                                    # PHP 오류 · 경고 확인
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8081       # 200 또는 302 = 떠 있음
cd characterization && npm test                                      # 동작 보존 테스트 (레거시 대상)
docker compose --profile php down && docker compose --profile php up -d   # 시드 데이터를 처음 상태로 되돌린다
```

- 이 모듈에는 단위 테스트가 없다. 동작 확인 수단은 `characterization/` 의 동작 보존 테스트와 화면 · `curl` 응답 비교다.
- 컨테이너를 다시 만들면 DB 는 시드 상태로 돌아간다. 데이터를 바꾸는 작업 전후에는 이 방법으로 상태를 맞춘다.

## 2. 작업 원칙 — 수정 전 영향도 분석 필수

레거시 코드는 문서 · 테스트가 없고, 비즈니스 규칙이 SQL 문자열과 화면 파일에 흩어져 있다. **어떤 수정이든 아래 순서를 지킨다.**

1. **읽기 먼저.** 고칠 함수뿐 아니라 그 함수를 호출하는 곳(`grep -rn "함수명" legacy/`)과 그 함수가 부르는 SQL · include 파일을 모두 연다.
2. **영향도 표를 먼저 답변으로 낸다.** 열: 바뀌는 파일:줄번호 / 영향받는 화면 · 요청 / 확인 방법. 사람이 승인하기 전에는 파일을 고치지 않는다.
3. **한 번에 한 규칙만** 바꾼다. 여러 동작 변경을 한 커밋에 섞지 않는다.
4. **수정 후 확인**은 `characterization/` 테스트 실행과, 바꾼 화면의 응답을 수정 전후로 `curl` 해 `diff` 하는 것으로 한다. 실행 결과를 답변에 적는다.

## 3. 근거 인용 규칙

- 코드의 동작을 설명하거나 규칙을 발견했다고 말할 때는 반드시 **`파일:줄번호`** 를 붙인다(예: `legacy/item-bank-php/search.php:214`). 근거 줄을 댈 수 없으면 "확인 필요"로 표시하고 단정하지 않는다.
- 주석과 코드가 다르면 **코드가 기준**이다. 다르다는 사실을 답변과 문서(`docs/<모듈>/BUSINESS-RULES.md`)에 남기고, 주석을 코드에 맞춰 고치는 것도 별도 변경으로 취급한다.
- 매직 넘버(예: `level < 5`, 페이지 크기 `20`)를 발견하면 값의 의미를 추측하지 말고 "의미 확인 필요"로 적는다. 사람이 뜻을 확정하면 그때 이름 붙인 상수로 뺀다.
- `vendor/` 아래 외부 라이브러리는 분석 · 인용 대상에서 제외한다.

## 4. 테스트 없는 구간의 작업 절차

수정할 코드에 대응하는 동작 보존 테스트가 없으면 **코드를 고치기 전에** 테스트를 먼저 만든다.

1. 대상 엔드포인트의 현재 응답을 `characterization/` 규칙대로 정규화해 스냅샷으로 찍는다(`cd characterization && npm run baseline -- <모듈명>`). 케이스는 정상 · 경계값 · 빈 결과를 포함해 최소 5개.
2. 스냅샷에 실행마다 바뀌는 값(시각 · 세션 · 토큰)이 섞였는지 확인하고 제거한다.
3. 그다음 코드를 고친다. 고친 뒤 `npm test` 가 초록이면 동작이 보존된 것이다. 의도한 동작 변경이라 스냅샷이 바뀌어야 하면, 바뀐 케이스 이름과 이유를 답변에 적고 사람의 확인을 받은 뒤 `baseline` 을 다시 찍는다.
4. 테스트를 만들 수 없는 구간(세션 의존, 외부 연동)은 "테스트 불가 사유"를 답변에 적고 수동 확인 절차를 대신 제안한다. 조용히 넘어가지 않는다.

## 5. 코딩 컨벤션 (레거시에 새로 넣는 코드에만 적용)

- 사용자 입력은 prepared statement 또는 `mysqli_real_escape_string` 을 거친다. SQL 문자열에 변수를 직접 이어 붙이지 않는다.
- 새 함수는 100줄을 넘기지 않는다. 기존의 긴 함수(`buildSearchQuery` 등)를 쪼개는 것은 별도 요청이 있을 때만 한다.
- 오류는 삼키지 않는다. `@` 억제 연산자와 빈 `catch` 를 새로 추가하지 않는다.
- 화면 출력은 `htmlspecialchars` 를 거친다.
- 기존 파일의 들여쓰기 · 따옴표 스타일을 그대로 따른다. 파일 전체 재포맷은 금지한다.

## 6. 금지 사항

- `legacy/` 는 이관 대상이다. **명시적 요청이 없는 한 수정하지 않는다.** 분석 · 문서화 요청에서는 읽기만 한다.
- 동작을 바꾸는 "개선"(정렬 기준, 기본값, 제외 조건 변경)을 리팩토링에 섞지 않는다. 발견한 문제는 목록으로 보고만 한다.
- DB 스키마 · 시드 SQL(`db/mariadb/init/`) 변경은 먼저 사람에게 묻는다.
- 응답 HTML 의 구조(`<table id="items">`, `#count`, `#message`)를 바꾸지 않는다. 동작 보존 테스트가 이 구조를 읽는다.
- `vendor/` 아래 파일을 고치지 않는다.
- 운영 DB 호스트에 접속하는 명령을 만들지 않는다. 로컬 compose 의 DB 만 쓴다.

## 7. 아키텍처 안내

```
legacy/item-bank-php/
├── index.php        메뉴 (문항 검색 · 문항 등록 · 단원 목록)
├── search.php       문항 검색. buildSearchQuery() 에 검색 규칙이 모여 있다 (500줄 이상)
├── register.php     문항 등록 · 검증 규칙 (제목 길이, 난이도 범위, 단원 필수)
├── units.php        단원 목록
├── inc/db.php       DB 연결 · inc/layout.php 공통 레이아웃
└── vendor/          외부 라이브러리 (읽지 않는다)
```

- 규칙이 숨어 있는 곳: 검색 조건 조합(단원 · 난이도 · 태그), 등록 · 수정 시 검증, 목록의 기본 정렬과 제외 조건. 이관 시 이 세 곳을 우선 대조한다.
- 문서화 결과는 `docs/<모듈>/ARCHITECTURE.md`, `BUSINESS-RULES.md`, `ERD.md` 에 쓴다. 규칙마다 근거 `파일:줄번호` 를 붙인다.

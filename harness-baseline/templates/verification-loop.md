# AI 검증루프 v1

버전: v1 · 2회차 (Day 2-1 실습 4에서 기준을 다듬고, Day 2-4에서 reviewer · tester Sub-agent 연결)
오늘 바뀐 점:
- 6절 판정 기준의 "충분한가" · "적절한가"를 예/아니오로 판정할 수 있는 문장으로 바꿨다.
- 4절 테스트 실행에 폴더별 명령을 적었다(modern/api · modern/web · characterization).
- 두 리뷰어(또는 reviewer 와 tester)가 엇갈릴 때의 처리를 8절에 추가했다.

AI 가 만든 변경분과 외주사 PR 을 머지하기 전에 거치는 절차다. **만든 쪽과 검증하는 쪽을 분리**하고, 판정은 `templates/approval-checklist.md` 의 네 기준으로 한다.

## 1. 왜 분리하나

만든 세션은 자기 코드를 옹호한다. 같은 컨텍스트 안에서 "잘 됐는지 확인해 주세요"라고 물으면 만든 이유를 다시 설명받을 뿐이다. 검증은 **변경분만 보는 새 컨텍스트**에서 한다.

## 2. 패턴

| 패턴 | 방법 | 쓰는 때 |
|---|---|---|
| 만든 세션 → 리뷰 세션 | 새 터미널에서 Claude Code 를 새로 띄워 diff 만 보게 한다 | 기본. 모든 변경 |
| Claude 생성 → 다른 모델 리뷰 | `codex exec` 등 다른 도구에 같은 diff 와 체크리스트를 넘긴다 | 중요한 변경의 교차 검증 |
| 리뷰어 Sub-agent | 읽기 전용 리뷰어(`.claude/agents/reviewer.md`)와 테스터(`tester.md`)에 위임한다. `/verify` 가 이 둘을 부른다 | 같은 세션 안에서 격리된 컨텍스트로 리뷰할 때 |

## 3. 역할

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 만든 세션 | 구현, 테스트 작성, 리뷰 결과 반영 | 자기 변경의 승인 판정 |
| 리뷰 세션 | diff 읽기, 체크리스트 대조, 테스트 실행, 이슈 목록과 판정 | **코드 수정.** 고치기 시작하면 그 순간 "만든 쪽"이 된다 |
| 사람 | 요청 범위 확정, 리뷰 이슈의 수용 · 기각, 최종 머지 | 리뷰어의 판정을 읽지 않고 머지 |

## 4. 절차

1. **요청 범위 확인.** 무엇을 요청했는지 한 문장으로 받는다. 범위가 주어지지 않았으면 판정하지 말고 먼저 묻는다.
2. **변경 파일 목록과 diff 읽기.** `git diff --stat <범위>` 로 목록을 먼저 보고, 파일마다 diff 를 읽는다. patch 파일이면 `git apply --stat` 으로 목록을 뽑는다.
3. **체크리스트 대조.** `templates/approval-checklist.md` 를 읽고 항목마다 충족 · 미충족 · 확인 필요 중 하나로 표시한다.
4. **테스트 실행.** 변경된 폴더의 테스트만 실행한다. 명령은 팀 `CLAUDE.md` 의 빌드 · 테스트 명령을 따른다. 결과는 통과 · 실패 수와 실패한 테스트 이름만 남기고 전체 로그를 대화에 싣지 않는다.
   - `modern/api` 가 바뀌었으면 `modern/api` 에서 `./gradlew test`
   - `modern/web` 이 바뀌었으면 `modern/web` 에서 `npm test`
   - 이관 코드는 `characterization` 에서 `npm test`(레거시 대상)와 `TARGET_BASE_URL=http://localhost:8080 npm test`(새 API 대상). 새 API 가 꺼져 있으면 실행하지 않고 사람에게 기동을 요청한다.
5. **판정.** 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 판정한다. 하나라도 미충족이면 반려.
6. **되돌리기.** 리뷰 결과를 만든 세션에 넘긴다. 만든 세션은 이슈마다 수용 · 기각을 사람과 정한 뒤 수용한 것만 고치고, 다시 2번부터 돈다.

## 5. 출력 형식

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 항목 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
```

- 이슈 한 건은 심각도(치명 / 경고 / 제안) · `파일:줄번호` · 근거 · 수정 방향 네 항목을 모두 채운다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 따로 적는다.

## 6. 판정 기준 (v1)

- 테스트 통과: 테스트 명령을 실제로 실행해 실패 0건이고, 새로 생기거나 동작이 바뀐 public 메서드 · 엔드포인트마다 테스트가 1개 이상 있으면 충족.
- 치명 이슈 0건: 비밀값 노출 · 데이터 손실 · 인증 · 권한 우회 · SQL 문자열 조립이 0건이면 충족. 정의는 `templates/approval-checklist.md` 의 심각도 정의를 따른다.
- 요청 범위 이탈 없음: 변경 파일이 모두 요청 문장으로 설명되고, 요청으로 설명되지 않는 변경이 0줄이면 충족(요청으로 설명되는 파일 안의 import 정리는 허용).
- 컨벤션 준수: 계층 규칙 위반과 빈 catch 가 0건이면 충족. 네이밍 · 형식 위반은 경고로만 남긴다. 항목은 팀 `CLAUDE.md` 와 `convention-check` Skill 을 기준으로 본다.

## 7. 하지 말 것

- 리뷰 세션은 코드를 수정하지 않는다. 보고만 한다.
- 테스트를 실행하지 않고 "통과"라고 쓰지 않는다. 실행할 수 없었으면(서버 꺼짐, 의존성 미설치) 그 사실을 적고 사람에게 기동을 요청한다.
- 요청 범위를 모르는 상태에서 "범위 이탈 없음"을 충족으로 표시하지 않는다.
- 이슈 0건이 나오면 "경고 · 제안 수준까지 다시 봐 달라"고 한 번 더 요청한다. 0건은 결과일 수도, 안 본 것일 수도 있다.

## 8. 리뷰가 엇갈릴 때

- 두 리뷰어(새 세션과 Codex, 또는 reviewer 와 tester) 중 한쪽이라도 치명을 보고하면 사람이 그 줄을 직접 열어 확인하기 전에는 승인하지 않는다.
- 한쪽만 잡은 경고 · 제안은 이슈 목록에 출처(어느 리뷰어)를 붙여 그대로 남긴다.
- reviewer 의 판정과 tester 의 실행 결과가 다르면(예: reviewer 는 테스트 있음, tester 는 실패) 엇갈린 지점을 그대로 적고 사람에게 묻는다.

# 레거시 모듈 문서화

분석 대상: $ARGUMENTS

- 첫 번째 인자가 모듈 경로, 나머지는 범위 제한입니다. 인자가 비어 있으면 어느 모듈인지 먼저 묻습니다.
- <모듈명> 은 폴더 이름이 아니라 item-bank | assignment | grade 중 하나입니다.
  legacy/item-bank-php → item-bank, legacy/assignment-thymeleaf → assignment, legacy/grade-mssql → grade

### 절차
1. 분석 계획을 먼저 보여 주고 승인을 받습니다. 단계마다 읽을 파일과 순서, 건너뛸 폴더(외부 라이브러리, 빌드 산출물), 위험해 보이는 지점을 적습니다. 인자에 범위 제한이 있으면 그 범위 밖의 파일은 읽지 않습니다.
2. 진입점과 의존 관계를 분석해 docs/<모듈명>/ARCHITECTURE.md 로 저장합니다.
   - 구성: 모듈 개요(5줄 이내) / 폴더 구조 / 진입점 표(URL 또는 화면 / 처음 실행되는 파일 / 주요 함수) / 의존 관계(mermaid flowchart 1개 + "A → B (A가 B를 호출)" 호출 표) / 가장 긴 함수 3개(파일, 이름, 시작 · 끝 라인, 하는 일) / 미확인 목록
3. 데이터 흐름을 분석해 docs/<모듈명>/ERD.md 로 저장합니다.
   - 테이블 목록(이름 / 주요 컬럼 / 근거), mermaid erDiagram 1개(관계마다 "선언" / "추정" 구분), 테이블별 읽기 · 쓰기 위치 표
4. 비즈니스 규칙 후보를 뽑아 docs/<모듈명>/BUSINESS-RULES.md 로 저장합니다. 매직 넘버는 따로 표로 모읍니다(값 / 위치 / 추정 의미).
5. 사람이 표본 점검할 규칙 3개를 추천합니다. 가장 그럴듯하고 깔끔한 규칙 1개, 주석과 코드가 다르거나 매직 넘버가 있는 규칙 1개, 맨 뒤 규칙 1개. 규칙마다 열어 볼 `sed -n` 범위를 적습니다.

단계가 끝날 때마다 결과를 파일로 저장한 뒤 다음 단계로 넘어갑니다. 다음 단계는 앞 단계의 파일을 먼저 읽고 시작합니다.

### 규칙 형식
- ID: BR-01 부터 순번
- 규칙: 한 문장. "~이면 ~한다" 형태
- 근거: 파일:줄번호 (여러 곳이면 모두)
- 근거 코드: 해당 라인의 코드 1~3줄을 그대로 인용
- 확신도: 확실(코드의 조건문 · SQL 로 확인) / 추정(이름이나 주석으로 짐작)
- 비고: 매직 넘버, 주석과 코드의 불일치, 같은 규칙이 여러 곳에 다르게 구현된 경우

### 하지 말 것
- 분석 대상 폴더의 파일은 읽기만 합니다. 고치지 않습니다.
- 존재하지 않는 함수 · 클래스 · 테이블 이름을 쓰지 않습니다. 문서에 적는 이름은 저장소에서 grep 으로 정의가 확인된 것만 씁니다.
- 호출 방향을 추측으로 쓰지 않습니다. 근거 라인에서 호출하는 쪽 파일을 확인하고 적습니다. include · require 는 호출이 아니라 포함으로 따로 적습니다.
- 코드에 없는 규칙을 업계 상식으로 채우지 않습니다. 주석만 보고 규칙을 쓰지 않습니다. 근거가 주석뿐이면 비고에 "주석만 있음"으로 적습니다.
- 주석과 코드가 다르면 코드를 기준으로 규칙을 쓰고, 주석 내용은 비고에 남깁니다.
- 조건문의 부등호와 숫자를 인용 코드와 한 번 더 대조합니다(< 와 <=, 5 와 4).
- 직접 열어 확인하지 못한 것은 "미확인"으로 남깁니다. 근거 파일:줄번호가 없는 문장은 문서에 넣지 않습니다.
